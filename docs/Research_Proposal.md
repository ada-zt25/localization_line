# 研究计划书（RP，重建版 v4）

**论文题目（拟）**
> **Execution Is Feedback, Not a Localizer: A Bug‑Type‑Gated Study of Line‑Level Fault Localization and a Static–Dynamic Feedback Loop for LLM Repository Issue Resolution**
> 中文：执行是反馈，而非定位信号——面向 LLM 仓库 Issue 修复的行级故障定位：bug 类型门控分析与静动结合反馈闭环

- 方向：将 LLM 集成进大型代码仓库（repository‑level issue resolution）
- 目标会议：CCF‑B（ICSME / SANER / ISSRE / ESEM / MSR 类）
- 约束：2 个月、单人、仅用现成 benchmark、仅需 API + 本机 Docker（无训练、无大算力）
- 日期：2026‑06；先验/探索性实验（样本 n=12–60、单次运行）已完成，用于确认问题与方法路线；正式实验将扩到 150–300 实例并给置信区间。前沿模型为 DeepSeek‑V3。

---

## 摘要
要让 LLM 修复真实 GitHub issue（SWE‑bench），第一步是在大型仓库中**定位**要编辑的代码；定位 recall 是修复率的硬上界。本文做三件事，构成一条逻辑链：**(C1) 查实问题**——系统证明在前沿模型上「**行级**定位」是真瓶颈且随真实度单调恶化（0.53→0.28→0.15），文件级（0.90）已基本解决；**(C2) 排除错误解法并解释**——在官方 Docker 中真跑失败测试，证伪「执行覆盖可作行级定位的**直接信号**」（覆盖两种粒度均不敌强静态 LLM），并提出**bug 类型门控**机制解释为何执行对行级「不透明」，对 2026 年「执行接地」热潮形成有依据的纠偏；**(C3) 给出正确解法**——提出**静动结合的执行‑反馈‑修复闭环**，把执行**从「直接信号」改造成「迭代反馈」**，首批结果显示其相对单次静态多召回 **+42%** 的决定性行（fraction‑recall 0.393→0.557），机制成立。本文诚实指出 C3 在「只需命中 1 行」的 Recall@k 上尚未超越静态（原因：预测行无置信排序 + 单文件设定下静态已封顶），并给出明确的下一步（多文件难设定 + 置信排序）。

---

## 1. 背景与问题
大型仓库常上千文件、数十万行，远超 LLM 上下文窗口 → 修 issue 必须先**定位**。**定位召回率是修复率的硬上界**：没被定位到的代码，下游再强也改不到。基准用社区标准 **SWE‑bench Verified**（500 真实实例）。

## 2. 研究链路（问题 → A → B → 缺口）
- **A：Agentless (FSE'25)**——分层、纯 LLM、无执行的静态定位；不足：靠词法/结构相似度，漏依赖相连代码，分层是单向漏斗。
- **B：LocAgent (ACL'25)**——依赖图多跳定位，文件级 92.7%；不足（2026 三篇独立工作确认）：行级 recall 仅 ~15%，靠「撒大网」维持召回。
- **缺口**：行级召回是新的、被独立复现的硬瓶颈；无人在前沿模型上系统刻画「为何失败」，也无人验证「执行能否解决它」。

## 3. 三个贡献（每个：发现问题 → 设计方法 → 得到结果）

### 贡献一（C1）：把「行级定位是前沿真瓶颈」查实
- **问题**：默认「定位已被大模型解决」或「换更大模型即可」；到底差在哪、前沿是否仍差，无人系统量化。
- **方法**：SWE‑bench Verified 上设计**按真实度递进的受控实验**（文件已给 → 自己找文件 → 多文件），并**跨规模对照**（前沿 DeepSeek‑V3 + 本地 qwen2.5‑coder:7b / gemma2:9b）。实验：P0 / P0‑big / P1 / P2。
- **结果**：文件级已解决（**0.90**），**行级是瓶颈**；行级 recall **随真实度单调恶化 0.53 → 0.28 → 0.15**；大文件出现**精确性墙**（过预测 1.9×→**5.8×**、precision 0.49→**0.20**）；**23%** 实例决定性行被完全漏掉。**前沿不消失** → 问题真实。

### 贡献二（C2）：证伪「执行覆盖即定位」+ 机制解释（纠偏）
- **问题**：2026「执行接地」热潮（DAIRA/Echo 等）默认「运行代码能帮定位」，但没人验证它对**行级**是否有用。
- **方法**：官方 Docker 镜像里**真跑**失败的复现测试（FAIL_TO_PASS）取覆盖，把「被执行的行」当定位信号，与强静态 LLM **同台对比**；并剖析失败机制。实验：EGL（覆盖）/ P3（报错文本）/ P4（可合成性）。
- **结果**：**纯执行覆盖被证伪**——精确执行行太稀疏（recall **0.33**）、放宽到被执行函数整段又太宽（**0.96 但占 85% 文件**），两种粒度都打不过静态 LLM（**0.42**）；报错**文本**注入同样无效（Δ **+0.00**）。机制 = **bug 类型门控**：崩溃类（~28%）异常在活动栈上抛出、traceback 直接点名出错行（执行有效）；**行为/断言类（~58–65%，多数）函数返回错值、返回后才被断言发现，此刻函数帧已弹出栈、覆盖又被 import 连锁淹没**（执行对行级「不透明」）。附：P4 表明「无信号」不是结构性墙（93% 可合成复现测试），故 C2 的失败归因于「信号性质」而非「信号缺失」。

### 贡献三（C3）：静动结合的执行‑反馈‑修复闭环（新方法）
- **问题**：既然「执行当直接信号」不行，执行**到底该怎么用**才能提升行级 recall？
- **方法**：把执行**从「直接答案」改造成「试错反馈」**——静态 LLM 先提出修复（以 **SEARCH/REPLACE 编辑块**输出，小输出避免 API 断流；**编辑即定位**）→ 在官方 Docker 跑 FAIL_TO_PASS → 取**新报错/失败形态**作反馈 → 据反馈**再定位补漏** → 迭代 **K=5** 轮 → 定位输出 = 各轮编辑行**并集**。即「静态看代码选候选 ⊕ 动态用真实失败反馈纠偏补漏」。实验：**hybrid_loop**（本方法，原代号 P8）。
- **结果**：相比单次静态，环路**多召回 +42%** 的决定性行（fraction‑recall **0.393 → 0.557**，Δ +0.164）；3/12 实例提升，**xarray‑4075 从 0 → 1.0**；解决率 8/12 → **机制成立**（执行作反馈能捞回静态漏掉的行）。**诚实局限**：在「只需命中 1 行」的 ARISE 同口径 Recall@k 上暂未赢静态（静态 66.7/83.3/100 vs hybrid_loop 8.3/66.7/91.7），主因 = hybrid_loop 预测行**无置信排序**（@1 吃亏）+ 单文件设定下**静态已封顶**；非定位质量问题。

> **三者是一条逻辑链：① 查实问题 → ② 排除错误解法并解释为什么错 → ③ 给出正确解法。**

## 4. 指标与定义
- **gold 行**：官方修复补丁实际改动的行（删除行 + 纯插入的相邻锚点）。
- **fraction‑recall**（主，刻画「完整性」）：|预测行 ∩ gold| / |gold|，逐实例后平均。
- **Line Recall@k**（ARISE 同口径）：实例级「top‑k 预测行含 ≥1 条 gold 行」的比例（需置信排序）。
- 文件级 recall@k；precision；过预测比 = |预测| / |gold|；上下文效率（recall@固定预算）。
- 执行类：覆盖行 = coverage.py 记录的被执行行；被调用函数 = 函数体有被执行行（区别于 import 时执行的顶层/def 头部行）。

## 5. 实验设置
- 数据：SWE‑bench Verified（HF datasets‑server 取元数据；按 base_commit 取文件；官方 Docker 镜像跑测试）。
- 模型：前沿 DeepSeek‑V3；本地 7–9B 跨规模对照。
- 代码：`prelim_localization/`（p0–p7 + `hybrid_loop.py`/`hybrid_loop_agentic.py` + `code_graph.py`(ARISE 式程序图) + `egl_makeorbreak.py` + `eval_recall_at_k.py` + `hybrid_loop_watchdog.py`，自包含）。
- 工程鲁棒性（hybrid_loop 能跑通的关键）：容器内 `timeout 240` 防 pytest 挂起；SEARCH/REPLACE 小输出防 API 断流；看门狗自动清理卡死容器。

## 6. 局限与下一步
- **C3 需在 ARISE 同口径上证明价值**：(a) 搬到**多文件/全仓库难设定**（静态有头room）；(b) 给 hybrid_loop 预测行加**置信排序**（按 edit‑block 输出顺序，而非行号）。目标：证明「静态 + 动态反馈 > 纯静态（ARISE）」。
- 先验样本小（n=12–60、单次）→ 正式扩到 150–300 实例、多次运行给置信区间；硬化工具链覆盖 sympy/sphinx/django。
- 时间表：W1–2 硬化工具链 + 扩 C1 数据；W3–5 多文件 hybrid_loop + 置信排序；W6 主实验/消融（含同口径 vs ARISE 静态基线）；W7–8 写作。

## 7. 新颖性定位（须区分）
- **T2L‑Agent (2025)**：trace→line，但 C/C++ 漏洞、消费现成 PoC、AST 非图。
- **DAIRA / Echo (2026)**：执行接地于 SWE‑bench，但报修复率/成本、**无行级与上下文效率视角**——本文给出「执行对行级不灵」的反例并把执行**重定位为反馈闭环**。
- **ARISE (2026)**：静态图 + 切片的**行级 SOTA**（Line Recall@1/5/10 = 41/62/74，Lite/Qwen‑32B）——本文的**同口径对照基线**。
- LocAgent / Agentless / SWE‑Explore：父类/动机/行级评测来源。
- **双卖点**：① 纯执行对行级不灵 + bug 类型门控机制（给热潮纠偏）；② 执行作反馈闭环的静动结合定位方法。

## 8. 风险与兜底
- 方法在 Recall@k 暂未赢 → 论文以 C1+C2（实证 + 机制）为稳固主干，C3 以「机制成立 + 完整性 +42%」立足，难设定结果为加分项。
- 工具链脆 → 限 pytest 原生仓库仍是多仓库研究。
- 最坏 → C1+C2 的实证/纠偏论文本身可投 CCF‑B。

> 历史：上一方向（未见库的成对 API 组合约束）已弃，死于「问题在前沿消失 + 方法信息天花板 + 自建数据集」。本方向规避：问题前沿**不消失**、benchmark **现成**、结论由**可执行实验**给出。
