# 2026-06-10 Simplug 五模型 × 方法对比实验报告

  

## 摘要

  

本轮实验在 simplug pair-critical benchmark 上，将模型维度从此前的 2 个扩充到 **5 个跨 4 家厂商的 7–9B 开源模型**，并对每个实验条件进行 **3 轮独立采样 + 多数投票**，以验证一个核心命题：

  

```text

API discovery 不等于 API composition correctness。CAPIR方法的API sequence无法解决API 配对约束错误，找到正确的 API、甚至拿到正确的 API 调用顺序，并不能保证模型正确处理 API 之间的配对约束。

```

  

结论：在 5 个不同厂商的模型上，**单纯注入 API 知识（API 清单 / 文档片段 / 甚至 oracle 调用顺序）均无法可靠消除 pair violation**（B0–B3 违规率普遍 50%–100%）；其中**编程能力更强的 `qwen2.5-coder:7b` 在问题区反而稳定地全部失败（B0–B3 违规率恒为 100%）**；而显式注入 gold pair rule（B4）能把违规率大幅压低（多数模型降至 0%–17%）。这表明 **API 配对约束是一个独立于 "API 知识本身"、跨模型普遍存在、且尚未被现有知识注入方式解决的问题**——即 PairCoder 的立足点。

  

---

  

## 1. 实验目的

  

延续 2026-06-08 双模型实验的核心问题，本轮在两个方向上加强证据：

  

1. **跨厂商普遍性**：此前仅在 qwen 家族 + gpt-oss 上验证，存在"是否只是某一家模型的毛病"的质疑。本轮引入 Meta、Google、Mistral 的模型，覆盖 4 家厂商。

2. **统计稳健性**：此前每个条件仅 1 个样本（n=6 任务，单轮），易受单次随机性影响。本轮每条件运行 3 轮并采用任务级多数投票，区分"系统性失败"与"偶然蒙对"。

  

核心待验证命题不变：

  

```text

当模型已经拿到正确 API 顺序（B3 oracle sequence）时，

是否仍会因为缺少显式 pair constraint 而生成错误代码？

```

## 2. 实验设置

  

### 2.1 模型（5 个，7–9B，4 家厂商）(Q2:需要和最前沿gpt，claude这些闭源模型对比)

  

| Model | 参数量 | 厂商 | 角色 |

|---|---:|---|---|

| `qwen2.5:7b` | 7B | 阿里 | 通用基线（旧 baseline） |

| `qwen2.5-coder:7b` | 7B | 阿里 | 代码专精模型（与上一行构成"通用 vs 代码"同家族同尺寸对照） |

| `llama3.1:8b` | 8B | Meta | 通用 |

| `gemma2:9b` | 9B | Google | 通用 |

| `mistral:7b` | 7B | Mistral（法国） | 通用 |

  

选型原则：参数量集中在 7–9B 同一档，消除"模型大小"这一混淆变量；保留 `qwen2.5:7b` vs `qwen2.5-coder:7b` 的受控对照；厂商多样化以排除家族特异性。

  

### 2.2 数据集与任务

  

数据集：`simplug`。任务数量：6 个 pair-critical tasks（T001–T006）。

  

任务覆盖的 pair constraints：

  

```text

sp.plugins_context -> sp.hooks.score （参数语义：需传 plugin name string，而非 plugin object）

sp.disable -> sp.hooks.score （共享 receiver / 状态依赖：需对同一 sp 操作）

sp.get_plugin -> wrapper.disable -> sp.hooks.score （返回值流向 / receiver 绑定）

```

  

### 2.3 方法（知识注入强度从弱到强）

  

| Method | 注入内容 | 目的 |

|---|---|---|

| `B0_direct` | 只给任务描述 | 无 API 知识下界 |

| `B1_api_list` | API 名称、签名、简短说明 | 测试"只知道有哪些 API"是否足够 |

| `B2_raw_api_docs` | 普通 API 文档片段 | 模拟 raw docs / RAG docs baseline |

| `B3_oracle_api_sequence` | 每个任务的正确 API 调用顺序 | **排除 API discovery / sequence 推荐错误**，专测 composition semantics |

| `B4_gold_pair_rule` | 人工 gold typed pair rule | Pair rule 上限（oracle upper-bound） |

  

### 2.4 评测方式

  

基于 AST 的 pair violation checker，主要检查：

  

1. `plugins_context(...)` 是否传入 plugin name string，而非 plugin object；

2. `sp.disable(...)` 是否使用正确的 plugin name string；

3. `sp.get_plugin(...)` 的返回值是否被用作 `wrapper.disable()` 的 receiver；

4. 是否存在必要的 `sp.hooks.score(...)` 调用；

5. 在"按名禁用"任务中是否误用 `plugins_context` 替代 `sp.disable`。

  

错误类型分类：`missing API call`（漏调用）、`wrong parameter semantics`（参数类型/语义错误）、`wrong API pattern`（用错 API 模式）、`broken data flow`（数据流断裂）、`syntax_error`（语法错误）。

  

### 2.5 评测器修复说明（与 06-08 版本的差异）

  

本轮在运行前修复了 checker 的若干边界条件，以消除假阳性、提高标签准确性：

  

1. **"漏调用" vs "参数错误"标签分离**：在 disable 类任务中，若 `sp.disable` 完全缺失，标记为 `missing API call`，而非旧版一律标记为 `wrong parameter semantics`。

2. **新增 `wrong API pattern` 检测**：在"按名禁用"任务中，若模型用 `plugins_context` 替代 `sp.disable`，即便它恰好也包含了一个正确的 `sp.disable` 调用，也判为违规——修复了旧版"无关的正确子调用蒙混过关"的假阳性。

3. **`get_plugin` 非字符串参数**：若 `sp.get_plugin` 以变量（plugin 对象）而非字符串名调用，标记为 `wrong parameter semantics`，而非旧版误报的 `broken data flow（缺少赋值）`。

4. **多轮 + 多数投票**：新增 `--runs` 支持每条件多轮采样；汇总时一个任务需在多数轮次（≥50%）通过才计为 pass。

> `Ollama问题存在性实验/paircoder_step0_simplug_pilot.py`、`run_comparison.sh`、`visualize_results.py`

## 5. 错误类型分布（B0–B3 失败样本，3 轮共计）

  

| Model | 错误标签总数 | missing API call | wrong param semantics | wrong API pattern | broken data flow | syntax |

|---|---:|---:|---:|---:|---:|---:|

| `qwen2.5:7b` | 61 | 35 | 16 | 6 | 3 | 1 |

| `qwen2.5-coder:7b` | 79 | 38 | 28 | 8 | 5 | 0 |

| `llama3.1:8b` | 70 | 38 | 22 | 0 | 7 | 3 |

| `gemma2:9b` | 48 | 30 | 15 | 0 | 3 | 0 |

| `mistral:7b` | 68 | 39 | 17 | 6 | 6 | 1 |

  

观察：

  

- 各模型主导错误均为 **`missing API call`**（漏掉必要的配对调用）与 **`wrong parameter semantics`**（参数类型/语义错误，典型为把 plugin 对象当成 name string 传入）。

- **`qwen2.5-coder:7b` 的错误总数最多（79），且 `wrong parameter semantics`（28）与 `wrong API pattern`（8）显著高于通用版 `qwen2.5:7b`**——代码模型有更强的"惯用写法"先验，更容易自作主张走偏。

> 在 simplug pair-critical benchmark 上，来自 4 家厂商（阿里、Meta、Google、Mistral）的 5 个 7–9B 开源模型，在所有缺少显式 pair rule 的知识注入条件下均产生大量 pairwise API composition violation（B0–B3 违规率 50%–100%），即便给定 oracle API 调用顺序亦然。尤为显著的是，编程能力更强的 `qwen2.5-coder:7b` 在问题区任务上**全部失败**（B0–B3 违规率恒为 100%），却在给定 gold pair rule 后**全部通过**（B4 违规率为 0%），表明瓶颈在于缺失配对知识而非模型能力。注入 gold typed pair rule 后，多数模型违规率降至 0%–17%（`mistral:7b` 为显著例外，仍达 50%，在固定任务子集上无法遵循显式规则）。这些结果确立了：API 配对组合是一个独立于 API discovery、跨模型普遍存在、且尚未被解决的问题。

## 6. 关键观察

  

### 6.1 问题跨厂商普遍存在

  

在 B0_direct（不给任何 API 知识）下，**5 个来自 4 家厂商的模型违规率全部为 100%**。没有任何一个模型能在缺乏配对知识时正确处理 simplug 的配对约束。这排除了"该问题只是某一家模型家族的特性"的质疑。

  

### 6.2 编程更强的 coder 在问题区反而稳定全错（核心证据）

  

`qwen2.5-coder:7b` 在 B0–B3 的违规率**恒为 100%**（24 个任务实例全部失败），而到 B4 则**恒为 0%**（6/6 全过），形成"悬崖式"对比：

  

```text

最强的代码模型：无配对规则时稳定 0/24 通过；有配对规则时稳定 6/6 通过。

```

  

与同家族同尺寸的通用模型 `qwen2.5:7b` 对照（后者在问题区还能零星通过 B1/B2/B3），可得稳健结论：

  

```text

编程能力更强 ≠ API 配对约束处理能力更强。

问题的瓶颈不在模型"能力"，而在缺少"配对知识"。

```

  

### 6.3 B3 oracle sequence 仍高违规——核心反证

  

即使提供了正确的 API 调用顺序（B3，已排除 API discovery / sequence 推荐错误），违规率仍然：`qwen2.5-coder` 与 `llama3.1` 为 100%、`qwen2.5` 为 83%、`gemma2` 与 `mistral` 为 50%。

  

这说明剩余错误**并非来自"用哪些 API、什么顺序"，而来自 API 之间的配对语义约束**（参数语义、返回值流向、receiver 绑定、状态依赖）——正是 pair rule 所承载、而 API list / docs / sequence 无法稳定表达的知识。

  

### 6.4 知识注入并非单调有效

  

更强的 API 知识并不保证更低的违规率：

  

- `qwen2.5:7b` 的 B3（0.83）反而比 B2（0.67）更差——给"oracle 顺序"还不如给文档片段；

- `qwen2.5-coder:7b` 在 B1/B2/B3 全为 1.00——**额外注入的 API 知识完全没有起作用**。

  

这从另一个角度证明："堆叠 API 知识"这条路径对 composition semantics 是不可靠的。

  

### 6.5 mistral:7b 是稳定可复现的异常点

  

`mistral:7b` 即使在 B4（已显式给出 gold pair rule）下仍有 50% 违规，且违规集中在固定任务（T003、T005、T006），**3 轮全部如此**，并非随机噪声：

  

- T003 / T006（按名禁用）：稳定地误用 `plugins_context` 替代 `sp.disable`；

- T005（仅 beta 的临时上下文）：稳定地把 plugin 对象当作 name string 传入。

  

这说明部分模型对"显式配对规则的遵循能力"本身较弱——即便规则已明确给出，仍无法消化为正确代码。

  

### 6.6 B4 上限并非对所有模型完美

  

B4 是 oracle 上限条件，但仅 `qwen2.5-coder` 与 `gemma2` 达到 0%；`qwen2.5` 与 `llama3.1` 仍有 0.17，`mistral` 高达 0.50。残余失败集中在 T006（同时按名禁用 alpha 与 gamma）。这提示：**pair rule 不仅要"给到"，还要以模型能消化的形式给到**，为后续自动配对方法（如何检索、如何呈现 pair rule）留出了改进空间。

> On the simplug pair-critical benchmark, five 7–9B open-source models from four vendors (Alibaba, Meta, Google, Mistral) all exhibit substantial pairwise API composition violations under every knowledge-injection condition that lacks an explicit pair rule (B0–B3 violation rates of 50%–100%), even when given oracle API call sequences. ## 8. 当前局限

  

1. 仍为 small-scale existence experiment，仅覆盖 simplug 的 6 个 pair-critical tasks；

2. `B4_gold_pair_rule` 是 oracle upper-bound，不代表自动 PairCoder 检索模块的最终效果；

3. `B2_raw_api_docs` 为手工整理的文档片段，非完整 RAG pipeline；

4. 尚未加入真实 CAPIR 复现或完整 retriever / reranker baseline；

5. 5 个模型均为本地可运行的 7–9B 开源模型，未覆盖闭源最强模型；

6. AST checker 为静态语义检查，未实际执行生成代码做运行时验证。

  

---

  

## 9. 下一步建议

  

1. 保留本轮五模型 × 方法 × 3 轮矩阵，作为问题存在性的主证据（跨厂商 + 统计稳健）；

2. 在另一个低资源库上复制同样矩阵，避免 simplug 单例化；

3. 将 `B4_gold_pair_rule` 替换为自动检索的 `PairCoder_retrieved_pair_rule`，形成完整方法对比；

4. 针对 6.6 的发现，研究 pair rule 的**呈现形式**（措辞 / 结构 / typed schema）对模型遵循率的影响；

5. 单独深入分析 `mistral:7b` 异常，作为"模型对显式规则遵循能力差异"的 case study；

6. 如资源允许，补充一个云端闭源强模型，验证 updated-LLM setting 下结论是否依然成立。
