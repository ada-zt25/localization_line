# Q3 离线门控结论 —— def-use 扩候选集（2026-06-25，无 GPU 免费跑出）

> 一句话:**def-use 扩候选集这个杠杆，把"候选集里有金标"的天花板抬了 +6.9(76.7→83.6),但任何重排都realize不出来(实测 R@10 ≈ 60.8 ≈ 不扩之前),因为扩进来的金标在 ~84 行 def-use 邻居里是 1 根针、没有任何排序信号能把它单独挑出来。要兑现这 +6.9 只能靠"第二次 LLM 判断"。**

## 怎么跑出来的(可复现，免费)
用昨天 AWQ 跑的 substrate dump(`archive/egl_e2e_awq.json`,233 个实例有底料),离线模拟 `region_loc._expand_voted`:
```bash
SWEBENCH_DATASET=lite python ablation_rank_sweep.py --substrate archive/egl_e2e_awq.json --grow-depth 1
```

## 结果(n=232)
| 指标 | 数值 | 含义 |
|---|---|---|
| ORACLE(set) | 76.7 | 投票集的"有金标"天花板(完美排序上限) |
| **EXPANDED(set)** | **83.6** | 投票集 + def-use 扩展后的天花板(**+6.9**) |
| v0_grow / graph_mass / sym_fuse (realized) | 59.9 / 60.8 / 60.8 | 实际重排扩展集的 R@10 —— **和不扩之前(59.9)一样** |

- 扩展深度 1 就饱和:depth 2/3、cap 60 都还是 83.6(金标的 def-use 邻居就在 1 跳内)。
- 16/232(6.9%)的实例因扩展"新捞到"了金标(都是投票全漏的)。
- 这些实例上:每文件扩进来 ~84 行,其中金标只有 ~1.8 行 → **信噪比 ~2%**。

## 为什么 realize 不出来
扩进来的金标行,和另外 ~24–82 个 def-use 非金标邻居,**长得一模一样**(都在切片里、图分相近、都没被投票)。任何只靠"投票质量 + 图分"的重排都无法把那 1 根金标针单独排进 top-10,强行提升它就会把真正被投票的金标挤出去 → 净效应 ≈ 0,R@5 甚至略降(噪声稀释)。

## 结论 & 下一步
1. **机械式 def-use 扩展 + 重排 = 死路**(天花板 +6.9,兑现 +0,R@5 略负)。这是离线门控替你省下的一次 GPU 空跑。
2. 要兑现这 +6.9,唯一可能是**第二次 LLM 判断**:把投票行 + def-use 邻居(~140 行)喂回模型,让它在 def-use 语境下重新挑。可行(haystack 不大)但**收益上限只有 +6.9**,且模型第一次就没投这些行,二次能否挑中存疑。
3. **更根本的发现**:bf16 诊断里 reg_ceiling 0.784 vs voted_ceiling 0.557 的 22 分缺口,**大部分不是 def-use 邻接的金标**(扩展只补回 6.9%)。所以瓶颈是"投票漏掉了区域内、但非数据流邻接的金标",真正的杠杆更可能在**投票本身**(更多采样 / 更好的 prompt / 对整个区域做二次 LLM 判断),而不是机械扩展。
