# 汇报讲稿（配套《行级故障定位_汇报.pptx》· v3）

> 14 页，建议 13–15 分钟。讲稿同时已写入 PPT 每页"演讲者备注"。
> 全场主线：**先用实证把"行级定位为何失败"讲透（C1）→ 再提出"静动结合的执行-反馈-修复闭环"作为方法创新（C2），并给出 hybrid_loop 的设计与首批结果**。
> 三个卖点：① 问题前沿鲁棒；② 纯执行对行级不灵 + 机制解释；③ 由此设计的"执行作反馈闭环"方法在"完整性"上已见增益。

---

## 1 · 封面（约 30s）
今天汇报：把大模型集成进大型代码仓库修 issue，第一步「定位要改的代码」是核心瓶颈，我聚焦更细的「**行级定位 recall 低**」。分两条线：先用实证把问题和成因讲透，再提出我设计的「**静动结合——执行-反馈-修复闭环**」定位方法。基准 SWE-bench Verified，前沿模型 DeepSeek-V3。

## 2 · 背景与问题（约 55s）
修真实 GitHub issue，仓库上千文件、放不进上下文，必须先定位。**定位召回率是修复率的硬上界**——漏掉的代码下游碰不到。文件级定位已做得好，真正卡住修复的是**行级定位 recall 低**。右边给体量：平均 1600 多文件、一次改 2.45 个文件。

## 3 · 研究链路 A→B→缺口（约 70s）
三步递进。**A（Agentless）**：分层、纯 LLM、无执行的静态定位，漏依赖相连代码、单向漏斗。**B（LocAgent）**：依赖图多跳，文件级 92.7%，但行级 recall 只有约 15%、靠撒大网。**缺口**：行级召回是新瓶颈，没人在前沿刻画"为何失败"、也没人验证"执行能不能救"——这正是我的切入点。

## 4 · 研究问题（约 55s）
三个问题递进。**RQ1** 问题刻画：行级定位多差、随真实度/文件规模怎么变、失败是召回还是精度。**RQ2** 诊断：执行覆盖/报错当「直接定位信号」能不能打败强静态 LLM。**RQ3（核心方法）**：不把执行当直接信号，而做成「执行—反馈—修复」闭环、和静态结合，靠动静结合提升行级 recall。

## 5 · 实验设计（C1 实证）（约 60s）
数据用 SWE-bench Verified，500 个真实实例；元数据从 HuggingFace 取，文件按提交号取，测试在官方 Docker 里真跑。模型用前沿 DeepSeek-V3，加本地 7–9B 做跨规模对照。指标：行级 recall、precision、文件级 recall、过预测比、上下文效率。下面是我设计的递进实验：P0 系列看粒度 gap 和精度墙；P1、P2 看真实/多文件；EGL 看覆盖能否做定位信号；P3、hybrid_loop 看执行反馈能否提升行级召回。

## 6 · 核心结果①问题真实（约 65s）
DeepSeek-V3 三种真实度下行级 recall：单文件文件已给 **0.53**，多文件真实 **0.28**，完整 agentic 独立基准约 **0.15**，单调恶化。要点：文件级不差（0.66–0.90），瓶颈在行级；多文件下连找全文件都只有 0.35；23% 实例决定性行被完全漏掉。**关键：问题在前沿不消失**。

## 7 · 核心结果②精确性墙（约 50s）
单文件按文件大小分层：随文件变大，**precision 从 0.49 掉到 0.20、过预测比 1.9→5.8 倍**。前沿在大文件上靠撒大网兜召回，是"找得到、找不准"。上下文效率是修复率的隐性约束。

## 8 · 核心发现③纯执行覆盖做不了行级定位（约 65s）
官方 Docker 里真跑失败测试取覆盖：精确执行行 recall 仅 **0.33**（决定性行常在未走分支/要新增的位置、没执行）；放宽到被执行函数整段 recall **0.96** 但占 **85% 文件**、没缩小范围。LLM 静态 **0.42**、只选约 9 行又窄又准，覆盖两种粒度都打不过。结论：覆盖作为「直接信号」被证伪——**但不代表执行没用，关键在怎么用**。

## 9 · 为什么纯执行对行级失灵（详细机制，约 80s，重点）
两条技术原因 + 一条根因。**原因一覆盖太宽**：pytest 一 import 连锁导入上百模块，每个模块顶层/def 头部行在导入时就执行，函数体只有被调用才执行，覆盖分不清二者。**原因二覆盖太稀疏**：决定性行常在没走到的分支或要新增的代码，从不执行、不在覆盖里。**根因 bug 类型门控**：崩溃类约 28%，异常在活动栈上抛出，traceback 直接点名出错行，执行有效；行为/断言类约 58–65%、是多数，函数返回错值、返回后才被断言发现，此刻函数帧已弹出栈、traceback 没有它，差分 SBFL 也救不了（buggy 是正常代码、通过测试也覆盖它），执行对行级"不透明"。

## 10 · 方法探索（一）：两条失败的执行设计 + 原因（约 55s）
我设计并验证了两条用执行的方法，都失败、但失败指明了正确用法。**设计 A 覆盖即定位（EGL）**：直接拿覆盖当"要改的行"——证伪（粒度两难 + 决定性行 off-path）。**设计 B 报错反馈注入**：把报错文本喂回 LLM 重定位——无效（行为类栈已弹出）。**关键启发：执行不该当直接信号，而应作迭代反馈驱动定位修正** → 引出静动结合闭环。

## 11 · 方法探索（二）：静动结合执行-反馈-修复闭环（hybrid_loop 方法，原代号 P8，约 75s，核心）
流程：**静态定位**给候选行 →**试修**以 **SEARCH/REPLACE 编辑块**输出（小输出避免 API 断流）→**执行**在官方 Docker 跑 FAIL_TO_PASS →拿**新报错/失败形态**作反馈 →据反馈**再定位**补漏，迭代 **5 轮**；定位输出 = 各轮编辑行**并集**（编辑即定位）。核心思想：静态负责"看代码选候选"，动态负责"用真实失败反馈纠偏补漏"——**执行是反馈、不是直接信号**，绕开前面证伪的失败模式。为什么能涨 recall：一次部分修复后测试以不同方式失败，新报错暴露第一次漏掉的位置，尤其多位置 bug。

## 12 · hybrid_loop 实验设计与结果（约 75s，诚实呈现）
**设计**：SWE-bench Verified 的 pytest 原生单文件实例、≤400 行、12 个，每个自带复现测试；官方 Docker 跑 5 轮、容器内超时兜底（这次零卡死零断流）；对照 round0（纯静态单次）vs loop（5 轮并集）；两个指标。
**结果是两个相反的故事，要如实讲**：
- **指标① fraction-recall（召回全部 gold 行的比例）—— hybrid_loop 赢**：round0 0.393 → **loop 0.557（Δ +0.164，相对 +42%）**；3/12 实例提升、xarray-4075 从 0→1.0、解决率 8/12。说明环路确实能捞回单次漏掉的决定性行（多行编辑场景）。
- **指标② ARISE 同口径 Recall@k（top-k 含 ≥1 gold 行）—— hybrid_loop 尚未赢**：静态 66.7/83.3/100，hybrid_loop 8.3/66.7/91.7。但主因不是定位差，而是 hybrid_loop 输出无置信排序（@1 吃亏）+ 单文件下静态已封顶。
**结论**：hybrid_loop 在"完整性"上有真实增益；要在 ARISE 头条指标上显出价值，需搬到**多文件难设定 + 给预测行加置信排序**——这是下一步。

## 13 · 三大贡献总览（约 55s）
把全场收成一条逻辑链、三个贡献,每个都是"发现问题→设计方法→得到结果"。
- **贡献①　行级定位是前沿真瓶颈**:问题——大模型"定位"真解决了吗、瓶颈在文件还是行、换大模型能消除吗?方法——按真实度递进 + 跨规模受控实验;结果——文件级已解决、行级是瓶颈,recall 0.53→0.28→0.15,前沿不消失。
- **贡献②　证伪"跑代码即定位"+ 机制(给热潮纠偏)**:问题——2026"执行接地"热潮默认跑代码能帮定位,对行级真的吗?方法——官方 Docker 真跑覆盖 vs 静态 + 机制剖析;结果——覆盖证伪(0.33 / 0.96@85% < 静态 0.42),根因 = bug 类型门控。
- **贡献③　静动结合执行-反馈-修复闭环(新方法)**:问题——执行不能当直接信号,那该怎么用?方法——执行作"反馈闭环"(猜→试→看错→再补,hybrid_loop);结果——多找回 +42%(0.39→0.56)、有实例 0→1.0,机制成立。
一句话:**查实问题 → 排错并解释 → 给出新方法。**

## 14 · 论文定位与贡献（约 50s）
CCF-B 的"实证刻画 + 方法创新"。**C1 实证刻画**：前沿 LLM 行级定位失败模式系统刻画——粒度 gap、真实度恶化 0.53→0.28→0.15、精确性墙、纯执行无效 + bug 类型门控，实验 P0–P3 + EGL。**C2 方法创新**：静动结合的执行-反馈-修复闭环（hybrid_loop），把执行当迭代反馈而非直接信号、与静态融合提升行级 recall——真实有效的创新方法，不做简单方法。新颖性须区分：T2L（C/C++）、DAIRA/Echo（执行接地但无行级/效率视角，我们给反例）、ARISE（静态行级 SOTA，对照）。**双卖点**：①纯执行对行级不灵 + 机制给热潮纠偏；②执行作反馈闭环的静动结合定位方法。谢谢，请老师指正。

## 预判 Q&A

**Q：round0 静态就到 0.39，为什么不是 SWE-bench 的 0.15？**
A：不同难度。0.39 是「单文件 + 文件已给」最易档（最难的"在上千文件里找文件"被省掉了）；0.15 是「全仓库 agentic 探索」最难档。同样一个 issue，给什么/要做什么不同，难度天差地别。

**Q：hybrid_loop 在 Recall@k 上输给静态，那它还有价值吗？**
A：有，但要看指标。Recall@k 只要命中 1 条 gold 行，且 hybrid_loop 的预测行没有置信排序、@1 吃亏；而单文件静态已封顶。hybrid_loop 真正的增益在 fraction-recall（召回全部 gold 行）+42%，对需要改多行的 issue 有用。要在 Recall@k 上显出来，需多文件难设定 + 置信排序。

**Q：覆盖/traceback 都失败了，凭什么信 hybrid_loop 闭环会成？**
A：失败有机制——纯执行当"直接信号"被 bug 类型门控挡住。hybrid_loop 不同：执行只作"反馈"，定位仍由静态做，执行用来在多轮里暴露"第一次漏掉的位置"。首批结果（+42% fraction-recall、xarray-4075 0→1.0）已支持这个机制成立。

**Q：先验样本小（n=12–60、单次）。**
A：是方向性结论，用于确认问题与方法路线；正式实验扩到 150–300 实例、多次运行给置信区间。

**Q：会不会"换更大模型就解决"？**
A：不会——0.53→0.28→0.15 全在前沿 DeepSeek-V3 上测，独立基准用强模型 agent 同样约 0.15。问题在前沿不消失。

**Q：和 DAIRA / Echo / ARISE 区别？**
A：DAIRA/Echo 是执行接地但报修复率/成本、无行级与效率视角，我们给出它们在行级上的反例并把执行重定位为"反馈闭环"；ARISE 是静态行级 SOTA（同口径对照）；T2L 做 C/C++ 漏洞、消费现成 PoC。
