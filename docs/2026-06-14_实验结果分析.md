# PairCoder 实验结果分析(四库 × 五模型,执行口径)

> ⚠️ **历史快照(已被基准重设计取代)**:本文分析的 msgspec/peewee/niquests 三库**先验过强**(B4 未超 B1),正是这一发现促成了基准重设计——这三库已被三个**私有合成库**(frameforge/keyvault/meshlink)替换。当前基准定义见 [PairCoder_Benchmark_完整说明](PairCoder_Benchmark_完整说明.md);新库实验结果待你在新管线上跑出后另行分析。本文保留作为"为何不能用强先验库"的实证依据。

> 2026-06-14 ｜ 数据来源:本地真实产物 `Ollama问题存在性实验/result/<lib>_5model/exec_eval/`(`exec_summary.md`、`exec_results.csv`、`figs/`)。所有数字与图表均为实测,未做任何修饰。基准与方法学见 [PairCoder_Benchmark_完整说明](PairCoder_Benchmark_完整说明.md)。

## 1. 实验设置(实测)

- **模型(5)**:`qwen2.5:7b`、`qwen2.5-coder:7b`、`llama3.1:8b`、`gemma2:9b`、`mistral:7b`(7–9B 本地模型,温度 0.2)。
- **库(4)× 任务(38)**:simplug 10、msgspec 10、peewee 9、niquests 9。
- **提示档位(5)**:B0 直给、B1 API 清单、B2 原始文档、B3 理想调用序列、B4 gold 成对规则。
- **重复**:每 (模型, 任务, 档位) **3 轮**;任务级**多数票**(≥2/3 过算过)。
- **总生成量**:simplug/msgspec 各 750、peewee/niquests 各 675 = **2850 次**。
- **判分**:执行式隐藏测试 oracle(只看运行时行为,绝不读源码);评测前各库**锚定套件全绿**(oracle 可信度门槛)。

## 2. 总体结果与核心发现

各库**按档位的任务级通过率**(实测,来自各 `figs/charts_summary.md`):

| 库 | B0 | B1 | B2 | B3 | **B4** | B4 − max(B0..B3) |
|---|---:|---:|---:|---:|---:|---:|
| **simplug** | 8% | 28% | 24% | 26% | **76%** | **+48 pt** |
| **msgspec** | 10% | 64% | 42% | 42% | **64%** | **+0 pt** |
| **peewee** | 58% | 47% | 62% | 67% | **62%** | **−5 pt** |
| **niquests** | 53% | 84% | 78% | 62% | **80%** | **−4 pt** |
| 四库均值 | 32% | 56% | 52% | 49% | **70%** | — |

**核心发现(诚实):gold 成对规则(B4)只在真正陌生的库(simplug)上压倒性领先(+48 pt);对 msgspec/peewee/niquests 这些模型有强先验的库,B4 并不优于"最好的非 gold 基线"——通常是 B1(纯 API 清单)就已追平甚至反超。**

- simplug 是为本实验构造、模型几乎无先验的库 → B0 仅 8%,B4 跃升到 76%,且明显高于 B1–B3。这正是"问题存在 + 注入成对约束有效"的强证据。
- msgspec/peewee/niquests 都是公开、文档完善、模型大量见过的库 → 仅给 API 清单(B1)模型就能用对,**B4 的成对规则边际贡献≈0 甚至略负**。peewee 尤甚:B0 已 58%,B4 62%,几乎打平。

> 这不是负面结果,而是一个**有定位价值的结论**:成对约束注入的收益,**与库的"未见程度"强相关**——越是模型没背过的库,注入 pair rule 越关键。它直接印证了 benchmark 设计中"必须用低流行度/未见库"的要求(P2)。

## 3. 逐库结果

### 3.1 simplug(插件;模型无先验)——主结论成立

按档位通过率 8% → 28% → 24% → 26% → **76%**,B4 断层领先。

![simplug 按档位通过率](../Ollama问题存在性实验/result/simplug_5model/exec_eval/figs/pass_by_method.png)

**按 pair 类型**(B0 / B4):lifecycle 0%→**90%**、param-dependency 0%→**80%**、return-flow 0%→**90%**、shared-receiver 0%→**100%**。B4 在这四类上几乎全解。**唯一反常**:config-return-contract 反而 B0 40% > B4 20%(见下方威胁分析 §6)。

![simplug method×pair_type](../Ollama问题存在性实验/result/simplug_5model/exec_eval/figs/heat_method_x_pairtype.png)

**按难度**:B4 把 hard 从 ≤13%(B0–B3)抬到 **87%**,easy/medium 也升到 67%/75%——**越难,B4 相对增益越大**,与"难任务才需成对知识"的预期一致。

![simplug method×difficulty](../Ollama问题存在性实验/result/simplug_5model/exec_eval/figs/heat_method_x_difficulty.png)

**失败构成**(run 级):B0–B3 大量 `exec_error`(如 qwen2.5:7b B0 30 份里 23 份执行错——幻觉 API/跑不起来),B4 后骤降(qwen2.5:7b B4 仅 1 份 exec_error)。数据见 `result/simplug_5model/exec_eval/exec_summary.md`。

### 3.2 msgspec(序列化;强先验)——B1 即追平 B4

按档位 10% → **64%** → 42% → 42% → **64%**。**B1 与 B4 并列最高**;B0 极低说明"裸考"不行,但一旦给出 API 清单(含 `type=`/`enc_hook=` 等),模型即能用对,gold 规则无额外收益。

![msgspec 按档位通过率](../Ollama问题存在性实验/result/msgspec_5model/exec_eval/figs/pass_by_method.png)

**按 pair 类型**:config-return-contract B0 20%→B1 68%→B4 56%;param-dependency 0%→50%→70%;return-flow 0%→67%→73%。三类都靠 B1 大幅起跳,B4 仅与 B1 同量级。

![msgspec method×pair_type](../Ollama问题存在性实验/result/msgspec_5model/exec_eval/figs/heat_method_x_pairtype.png)

**按难度**:B4 在 hard 上 60%、medium 64%;B1 在 hard 仅 40%——这是 B4 相对 B1 唯一可见的优势(难任务上略强)。

### 3.3 peewee(关系数据库;最强先验)——档位几乎不影响

按档位 58% → 47% → 62% → 67% → 62%,**B0 已高、B4 未超 B3**。peewee 的 ORM 习惯模型烂熟,提示几乎不改变结果。

![peewee 按档位通过率](../Ollama问题存在性实验/result/peewee_5model/exec_eval/figs/pass_by_method.png)

**按 pair 类型**:大多数类型各档位都在 60–100%;**唯独 lifecycle 全档位 0%**——这是 savepoint 嵌套任务(P005),**所有模型、所有档位、含 B4 全军覆没**。这是一个干净的"难点定位":savepoint 的嵌套回滚语义是模型的共同盲区,且 gold 规则也没救回来(规则文本不足以让模型正确组织嵌套 atomic)。

![peewee method×pair_type](../Ollama问题存在性实验/result/peewee_5model/exec_eval/figs/heat_method_x_pairtype.png)

**按难度**:easy 87–93%、medium 47–80%、**hard 仅 13–33%**(含 B4 20%)——难任务(原子性/savepoint)是瓶颈,与提示档位基本无关。

### 3.4 niquests(HTTP;强先验)——B1 最高,param-dependency 顽固

按档位 53% → **84%** → 78% → 62% → 80%,**B1 最高、略高于 B4**。

![niquests 按档位通过率](../Ollama问题存在性实验/result/niquests_5model/exec_eval/figs/pass_by_method.png)

**按 pair 类型**:completion-obligation/lifecycle/return-flow/shared-receiver 在 B1/B2/B4 下普遍 90–100%;**唯独 param-dependency 卡在 20–40%(所有档位,含 B4)**——即 `json=` vs `data=`、`params=` 这组请求构造约束是顽固盲区,gold 规则也没显著改善。

![niquests method×pair_type](../Ollama问题存在性实验/result/niquests_5model/exec_eval/figs/heat_method_x_pairtype.png)

> niquests 任务只有 easy/medium 两档(无 hard),故难度热力图只有两列。

## 4. 跨库综合分析

1. **B4 的收益高度依赖"库的陌生度"**:simplug(+48 pt)≫ msgspec(0)≈ niquests(−4)≈ peewee(−5)。结论:**pair rule 注入对未见库才关键**;对模型已熟悉的库,单 API 清单(B1)即够。
2. **B0(裸考)的差异即"先验强度"探针**:simplug/msgspec B0 仅 8%/10%(无先验),peewee/niquests B0 高达 58%/53%(强先验)。B0 越低,B4 的相对空间越大。
3. **每类 pair 都各有"顽固盲区",且 gold 规则未必能解**:
   - peewee **lifecycle(savepoint)**:全档位 0%。
   - niquests **param-dependency(json/data/params)**:全档位 20–40%。
   - simplug **config-return-contract 在 B4 下反降**(20%)。
   这些是后续方法改进(更强的成对推理注入、或带反例的规则)的明确靶点。
4. **难度分层有效**:simplug/peewee/msgspec 都呈 easy > medium > hard 的单调下降;B4 的相对增益在 hard 上最大(simplug)或仅在 hard 上可见(msgspec)。分层让"提示在难任务上才起决定作用"清晰可见。

## 5. Oracle 可信度:静态 vs 执行(simplug,n=750)

simplug 同时有静态 checker 与执行 oracle 两套判分,可量化静态尺子的信度(数据 `result/simplug_5model/exec_eval/exec_summary.md` 与 `disagreements.csv`):

| | exec 过 | exec 挂 |
|---|---:|---:|
| 静态过 | 232 | **209** |
| 静态挂 | 7 | 302 |

- **一致率 0.712,Cohen's κ 0.459**。
- **209 例"静态过、执行挂"**:静态尺子太松——尤其新增的 config-return-contract(T007/T008)与机制类任务,静态只看到 `hooks.score` 被调用就放行,看不到返回值形态/运行时错误。
- **7 例"静态挂、执行过"**:静态对语义等价写法的误判(假阳性)。

> 这比早期 P1(6 任务,κ=0.83)的一致率更低,**正是因为新增的第 5 类(config-return)等任务对静态检查不可见**——构成"静态检查在这些 pair 类型上失效、必须用执行 oracle"的更强证据。锚定套件全绿则保证执行 oracle 本身可信。

## 6. 威胁与诚实说明(Threats to Validity)

- **B4 未在 3/4 库领先**:如 §2/§4,这是真实结果而非缺陷——它界定了方法的适用边界(未见库)。论文应据此把主张限定为"**面向未见/低流行度库**的成对约束注入"。
- **simplug config-return-contract 在 B4 下反降(40%→20%)**:疑因 gold 规则文本(强调"返回单值、勿包列表")诱导部分模型走偏,或该两任务(T007/T008,FIRST/LAST 单值语义)与 B4 规则措辞冲突。需逐 verdict 复核 `result/simplug_5model/exec_eval/verdicts/` 定位,属规则措辞问题而非 oracle 问题(锚定已证 oracle 正确)。
- **顽固盲区**(peewee savepoint 0%、niquests param-dependency 20–40%):说明部分 pair 约束仅靠"塞规则进 prompt"不足以解决,指向更强的注入/推理方法。
- **样本与档位**:n=每库 9–10 任务、5 模型、3 轮;peewee/niquests 缺 hard 档(niquests 无 hard 任务)。每类 pair 尚未达 ≥10 的规模(见基准文档 §4 缺口),置信区间/显著性检验待扩样本后补(P6)。
- **模型档位**:仅 7–9B 本地模型,未含前沿模型(P7)。

---

## 7. 对论文主张的意义

1. **存在性 + 干预有效**(RQ1/RQ2)在 **simplug** 上强成立:B0 8% → B4 76%,且 B4 ≫ B1–B3,尤其在 lifecycle/param-dependency/hard 上。
2. **泛化的边界**(RQ3):效果**条件成立**——取决于库的未见程度。这把"低流行度/未见库"从设计约束升级为**实证依据**,是一个比"B4 处处最好"更扎实、更可发表的结论。
3. **执行 oracle 不可替代**(RQ4):静态尺子在新 pair 类型上 κ 仅 0.459、209 例漏判,执行 oracle + 锚定门槛是可信度的根基。
4. **下一步靶点**:对"强先验库 B4 无增益"与"顽固盲区(savepoint、json/data)"两类现象,改进注入方式(带反例/带验证的成对推理单元),并补足每类 pair 任务量与前沿模型。
