# 文件定位冲 ≥90 recall —— SOTA 方案(2026-06-25，多 agent 搜索+对抗核验)

## 一句话结论
**≥90 file recall 在 top-5 / top-10 可达,在 top-1 不可达。** 换一个为"issue→代码定位"专门微调过的检索器 **SweRankEmbed** 即可,无需训练。

## 推荐:SweRankEmbed-Large 当冻结检索器(抬天花板的那一步)
- 模型:`Salesforce/SweRankEmbed-Large`(7B 双编码器,公开权重,CC-BY-NC-4.0 科研可用);小号 `SweRankEmbed-Small`(137M,甚至能 CPU 跑)。
- 用法:在**函数粒度**检索 → 函数分数按 max 聚合到文件 → 取 top-k 文件。仓库 [SalesforceAIResearch/SweRank](https://github.com/SalesforceAIResearch/SweRank) 有现成脚本 + 预处理好的 Lite。索引预算一次、永久复用,正好契合我们"跑一次冻结"的设计。
- **为什么是它**:瓶颈是"候选集召回"不是排序;重排只能在检索结果里重排、**永远超不过检索器的召回**(SweRank 原文明说)。所以**换检索器**才是抬天花板,重排只动 R@1。SweRankEmbed 是专门对比学习微调过的(这正是我们通用 Agentless 检索器缺的)。

## 诚实的预期数(全 300 Lite，我们"top-k 里有≥1 个金标文件"口径)
| k | SweRank 论文报告(严格/274子集) | 我们设置下的诚实预期 |
|---|---|---|
| R@1 | 72.63 | ~0.70–0.78(加 rerank ~0.80) |
| R@5 | 94.16 | **~0.90–0.93** |
| R@10 | (论文无 Lite@10) | **~0.92–0.94** |

**≥90 在 R@1 做不到**(任何已验证开源方法最高 file Acc@1 ~83,还是带 33B 重排器、严格子集);**≥90 只能在 k≥5(top-10 稳)**。这是**待复现的假设、不是已交付数字**,必须在全 300 上用我们口径重测。

## 集成(干净 drop-in)
1. 下载 `SweRankEmbed-Large` 到服务机,用 `sentence-transformers` 起(不用 vLLM)。
2. 新建 `swerank_loc.py`(~150 行):复用现有 AST 切函数 → 嵌入所有函数(索引缓存到 `cache/`,按 `repo@commit`)→ 嵌入 issue → cosine 取 top-N 函数 → max 聚合到文件 → 返回排序文件列表。
3. `egl_e2e.py` 加一个分支 `elif file_loc == "swerank":`(和 agentless/arise 并列),`--file-loc` 增加 `swerank` 选项。
4. 跑一次 `--file-loc swerank --topk 10` → `egl_e2e_swerank.json`,之后所有行定位实验 `--reuse-files egl_e2e_swerank.json` 复用。
5. 现有 `file_R@{k}` 逻辑直接读 R@1/5/10。工程量:中(一个新模块 + 两行 dispatch + 一次建索引),无训练、无 agent 循环。

## 备选
- **B1 先做(免费自检)**:先量我们**现有 Agentless 的 recall@20/@50**,以及 **Agentless ∪ SweRankEmbed ∪ BM25 的并集 top-10**——并集一定抬召回,这是"0.90 是不是已经够得着"的最便宜测试。
- **B2**:`SweRankEmbed-Small`(137M)当低成本兜底,@5 ~0.87–0.90、@10 ~0.92。
- **B3**(只有当 R@1 重要时):用 `SweRankLLM-Large`(33B,已开源)或我们的 Qwen-32B 做 listwise 重排,R@1 ~73→~80;**不抬 R@10 天花板**。

## 被否决的对比(口径陷阱)
- LocAgent "92.7%" = Acc@5 严格/274 子集 + 微调,换我们口径 ≈ 0.74。
- CoSIL(同款 Qwen2.5-Coder-32B,我们的口径)@5 只到 **0.837**(Lite)。
- 所有 agentic 方法都 < 检索器路线。
